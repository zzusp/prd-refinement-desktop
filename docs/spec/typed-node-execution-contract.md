# 类型化节点执行契约方案

## 目标与范围

本方案替代 `structured-model-output.md` 的局部修复方案。当前仅设计，不代表已经实施。

目标：每个节点在调用前有明确入参，模型通过固定结果提交契约产出候选，平台校验并提交正式结果后才推进下游；可恢复错误在对应工作单元内处理，永久错误明确保留，已成功工作可以恢复。

保留现有 Codex 登录方式、用户 Runtime 配置与按业务职责拆批方式；不恢复平台估算 token 门禁，不要求改用 Cortex 网关，不复制 Cortex 的整套 DBOS 基础设施。

参考代码基线：Cortex `88445d054f4a5a2595db12c8714458c6f7aff6d8`。

- `desktop/src/main/runtime/experts/expertModelClient.ts`：命名参数形式的类型化操作接口。
- `desktop/src/main/runtime/experts/gatewayModelClient.ts`：固定结果函数、参数提交、传输完整性及错误分类。
- `desktop/src/experts/audit/workflow.ts`：操作回执、校验、暂时故障重试及修正轮次。
- `nomad/src/experts/content/{domain,workflow}.ts`：领域 Schema、输入校验、输出 Schema 生成和业务验收。

## 当前问题

1. `scheduler-v2.ts` 的节点使用长位置参数；部分节点根据中文标题选择行为，输出结构主要写在提示词中。
2. Schema、TypeScript 类型、提示词示例和手写字段校验分别维护；细化 Schema 允许空证据数组，但领域校验拒绝。
3. 只有 `details-*` 显式传 Schema；核查、修正、调整、建议生成、资料图片识别等路径仍可能绕过。
4. `ask()` 将 JSON 语法失败与字段、引用错误放入同一个两轮循环，修正请求未携带完整失败候选。
5. DSH 的 `promptAndWait` 不接收新增 Schema 参数，公共接口无法保证适配器履行契约。
6. 细化结果在一个功能全部批次完成后才缓存；其中一个批次失败，会丢失其他已完成批次的可恢复成果。
7. 同源 PRD 重新分析会改变功能编号和批次，不能用两次 `F-003` 名称相同作为原失败输入回归依据。

## 一、以领域契约定义节点

每个节点明确三类数据：

- Input：平台传给节点的输入对象，包含冻结证据及必要的上游正式结果。
- Proposal：模型允许提交的候选参数，只含需要模型判断的内容。
- Result：平台验收候选后生成的正式结果，下游只能消费该类型。

采用 Zod 作为结构契约的单一来源，新增这一依赖用于同时推导 TypeScript 类型和运行时结构校验，并生成可表达的 JSON Schema。引用关系、跨项一致性、来源覆盖等上下文规则继续复用现有领域函数。结构层与上下文校验各司其职，不重复定义字段类型和必填条件。

传输 Schema 从 Proposal 结构生成，不直接使用包含内部身份和状态的完整 Result Schema。无法编码到供应商 Schema 的业务约束由本地校验保留；不得为适配供应商删除业务约束，也不得把所有字段一律设为必填或允许 null。

节点定义示意：

```ts
const refineDetails = defineNode({
  id: 'refine-details',
  version: 1,
  input: DetailInput,
  proposal: DetailProposal,
  result: DetailResult,
  submission: { name: 'submit_details', description: '提交当前功能批次的需求与澄清候选' },
  instructions: detailInstructions,
  validate: validateDetailEvidence,
  materialize: materializeAcceptedDetails,
});

const result = await executor.run(refineDetails, {
  workItemId,
  input: { feature, applicableConstraints, sourceUnits, evidenceCatalog },
  signal,
});
```

以上为设计示意。`defineNode` 是轻量类型与契约封装；工作流仍使用普通异步代码，不新增通用 DAG 配置系统。

输入校验在调用 Runtime 前执行：字段形状、证据目录、已有 ID、当前输入版本、必需上游结果均合法才允许调用。输入不合法归平台组装错误，不让模型修复平台入参。

模型仅选择证据 ID 和提交业务内容；来源位置、内部来源绑定、正式 ID、初始状态和版本由平台根据已验证事实生成。澄清候选按 blocking、suggestion、ignorable 分支定义，条件必填只属于对应分支。

## 二、统一模型操作入口

模型操作接口只执行一次候选生成，接收命名参数对象：

```ts
interface ModelOperationRequest {
  operationId: string;
  instructions: string;
  input: unknown;
  submission: {
    name: string;
    description: string;
    parameters: JsonSchema;
  };
  signal: AbortSignal;
}
```

实际接口还保留现有图片、模型配置和超时能力。返回值包含候选对象、传输完成状态及真实用量；Runtime 不提交正式业务结果，不自行嵌套业务修正循环。

### 通道落地边界

- 支持原生 function calling 的通道：注册唯一结果提交方法，以 tool choice 指定方法，接收其 arguments；拒绝错误方法和多个歧义提交。
- 当前 Codex CLI：复用已验证的原生结构化输出能力，将同一 Proposal 的传输 Schema 映射到 `--output-schema`，由适配器读取完整结果并返回候选对象。它是该通道的明确实现，不声称 CLI 目前已经支持我们注册的 forced function。普通对话文本不能成为备用结果来源。
- DSH：实施时先读取当前安装版本的结构化操作协议并做本地能力探针，不能依据 Cortex 历史补丁推定当前支持 `model/structured`。支持则接入同一候选契约；不支持则在运行前明确报告该适配器缺少结构化操作能力。保留配置和历史资料，不静默吞掉 Schema，也不自动切换认证或供应商。

这里复用 Cortex 的类型化提交接口及错误处理原则，不以引入新网关或改认证作为实现前提。结构化输出和函数参数提交都是传输手段，正式业务验收权归节点执行层。

## 三、明确节点执行顺序

1. 验证 Input，确定 work item 身份与契约版本。
2. 检查同输入、同契约的成功回执，命中则恢复正式结果。
3. 发起一次结构化模型操作，完整接收候选和结束事件。
4. 保存候选尝试；传输不完整时保存可用诊断，但不生成成功回执。
5. 用 Proposal Schema 校验形状，使用上下文 validator 验证证据与业务规则。
6. 不合格时返回结构化问题列表，例如 `{code, path, expected, actual, relatedIds}`；不以错误文案正则决定流程。
7. 合格候选经确定性 materialize 生成 Result，再校验 Result。
8. 原子保存正式结果和成功回执，之后才向下游返回。

候选不合格属于预期的验收结果；平台编程错误、持久化错误等走明确异常路径，不将任何异常都包装成可修正的模型输出。

## 四、异常分类与恢复策略

| 类型 | 判据 | 处理 |
| --- | --- | --- |
| 平台入参错误 | Input Schema 或输入关系校验失败 | 调用前停止该工作单元，记录平台错误，模型调用次数为零 |
| 暂时传输故障 | 可识别的连接失败、限流、临时服务错误、未完整结束的流 | 默认初次调用后最多重试 2 次；不占业务修正次数 |
| 结果提交协议错误 | 方法缺失或不匹配、完整响应中的损坏 JSON、根对象类型错误 | 默认最多重新提交 1 次；保存前后错误，仍失败则记 protocol failure |
| 候选字段或引用不合格 | Proposal 或领域 validator 返回问题 | 最多修正 2 轮；携带原始输入、上一候选和完整机器错误 |
| 业务上确实未定 | 合法的澄清候选 | 验收后保存为业务待处理项，不伪装成执行异常 |
| 认证或请求不支持 | 明确的认证、权限、参数或能力拒绝 | 直接报告配置/能力问题，不重复调用 |
| 供应商上下文或输出截断 | Runtime 原生终止原因 | 记录实际原因，不按平台估算 token 拒绝，也不原样无限重试 |
| 取消或失效执行 | 取消信号、任务版本或执行身份不匹配 | 终止对应调用，拒绝迟到结果提交 |
| 程序缺陷、写盘失败 | 非模型候选校验失败 | 记录平台故障，保留已有成功结果，不吞错 |

计数都属于同一 work item 的持久记录；传输与协议计数在该 work item 内累计，不在每轮业务修正时重置，从而避免多层重试次数相乘。只有用户显式发起新尝试才建立新的尝试记录，历史保留。

Runtime 不暴露原生错误分类时保留 runtime failure，不根据一段泛化错误文本猜测网络、截断或业务原因。

取消必须贯穿队列、模型调用、校验与提交。超时后先确认旧调用结束，再启动下一次，避免旧调用仍在运行而并发重试。

## 五、按工作单元持久化，支持真正的续跑

复用当前检查点、原子写入与任务 attempt 机制，抽取统一执行回执。暂不引入 DBOS 或新数据库。

- 细化工作单元是“功能 + 冻结批次”，不是整功能。
- 核查、修正、复核等按各自明确的业务工作单元保存回执。
- 回执绑定 task/execution、nodeId、contractVersion、workItemId、完整 Input 哈希和实际模型配置摘要。
- 保存独立的传输尝试、协议尝试、业务修正轮次、用量、候选诊断和正式结果引用。
- 输入、契约或结果不匹配时不复用；检查点里不能只凭数组非空判断成功。
- 独立工作单元继续完成并保存；依赖失败结果的下游不运行。全部单元收敛后再按领域规则汇总状态。
- 多批次合并时使用稳定批次标识和确定性 ID 映射，恢复与重复提交不能产生重复需求。

新执行协议升级 Pipeline。旧任务保留原错误和历史记录；从其冻结输入建立新协议任务，不改写旧检查点伪装新结果。新协议内部的失败恢复必须精确到工作单元。

## 六、迁移全部实际 JSON 调用入口

| 入口 | 改造重点 |
| --- | --- |
| 资料图片识别及分析中的图片读取 | 共用图片输入/转录候选契约与执行入口 |
| 本次补充说明理解 | 固定输入分类及条件字段，输出逐项对应输入 |
| 功能候选、候选返工 | 候选与来源处置共同校验，禁止半份结果提交 |
| 功能统一 | 明确成功、请求原文、分类返工三种结果分支，由代码处理状态转移 |
| 逐功能细化 | 业务内容与证据成对提交，批次级恢复 |
| 依据核查及关系结果 | 统一出参契约，执行故障不写成业务审计问题 |
| 有据修正与修正复核 | 独立 Patch/Review 契约，禁止误用完整 Detail Result |
| 澄清建议生成 | 建议必须绑定当前澄清及依据，使用统一队列和错误分类 |
| 后续调整的解析、生成、修正、复核 | 显式 nodeId 和契约；去掉按中文 title 猜节点和 `value => value` 绕过验收 |

## 七、验收与交付状态

修复不能承诺模型永不异常；可验证目标是错误在正确层分类、候选不会污染正式结果、成功工作不会丢失、故障恢复有界且可观测。

必须验证：

1. 所有实际模型 JSON 入口都有必需契约；不允许遗漏 Schema 或绕过统一执行器。
2. 非法入参零模型调用；非空证据、枚举和澄清条件必填有正反例；传输 Schema 与本地结构规则差异均有明确依据。
3. 错方法、损坏参数、分片中文、缺失结束事件、截断、认证失败、限流、取消等故障注入，断言错误类别和精确调用次数。
4. 业务修正请求确实包含上一候选和完整机器错误；多个错误可在同轮修正，耗尽不会无限循环。
5. 一个功能多个批次中一批失败，续跑只补该批；重启、重复提交、迟到响应不重复写入或覆盖成功成果。
6. 从 `T-1F2FBCF6` 保存冻结的原失败节点输入、候选和错误作为回归样本。缺少完整请求时明确重建方式及差异，不能声称精确重放。
7. 同源真实任务走完整流程，独立检查任务状态、平台问题、正式数据及交付包。功能编号不能作为跨任务输入身份。
8. 重启实际 Electron，验证用户入口调用新协议及真实恢复；源码、测试、进程和产品结果分别留证。

当前任务层 `blocked/draft` 与包内 `ready` 的不一致也需要在结果投影处统一：遵守既有“待处理项随需求进入包”的产品约束，业务待确认不阻止可交付需求包生成；相关需求保留明确待处理标识。未通过平台验收的结果只可进入明确标注的草稿，不能标为已完成核查。
