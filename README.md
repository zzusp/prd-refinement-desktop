# 需求细化平台

需求细化平台是一款面向中大型需求的桌面工具，用来在开发开始前，把一份定版 PRD 整理为模块下的简短需求检查清单。

中大型 PRD 往往包含大量功能、规则、字段、例外和跨模块约束。直接把整份 PRD 交给 AI 编码，容易在长文本中漏掉功能或细节，而且完成后也很难判断究竟覆盖了多少。这个工具先把 PRD 中的要求逐项拆开，并保留每项需求对应的原文依据。后续无论由 AI 还是人工开发，都应先完整阅读 PRD，再按清单逐项查漏，减少遗漏。

## 它能做什么

- 读取 HTML、DOC、DOCX、PDF、Markdown、TXT 等格式的定版 PRD。
- 按模块整理 PRD 明确要求，每条用简短文本指向原文；保留跨功能约束与完整待处理事项。
- 为每项结果保留原文内容及位置，方便回查为什么有这条需求。
- 区分已明确的需求、需要业务确认的问题和平台需要继续整理的问题。
- 支持按实际开发范围标记“本期做”或“本期不做”。
- 生成编码 Agent 可逐项核对的 CSV 清单，以及原始 PRD、待处理事项和 Excel 交付包。

它不是一键生成代码的工具，也不会替代产品、研发或测试做最终业务判断。它解决的是编码之前的需求整理问题：先把要做什么拆清楚，再逐项开发和验收。

## 适合什么时候用

适合这些场景：

- PRD 篇幅较长，包含多个功能、角色、状态或业务流程。
- 需求分散在正文、表格、附录和补充资料中。
- 计划让 AI 参与开发，但担心一次性处理整份 PRD 时漏项。
- 需要把需求交给多人或多个 Agent 分工，并统一核对完成范围。
- 上线前需要按原文逐项检查功能和细节是否已经落实。

对于只有几条明确改动的小需求，直接整理任务清单通常更高效，不一定需要使用本工具。

## 怎么用

1. 在“Runtime 配置”中配置可用的 AI Runtime，并完成连接检查。
2. 新建任务，选择一份定版主 PRD。
3. 按需添加补充文档、历史资料或背景说明。
4. 点击“开始分析”，等待平台读取资料并拆分需求。
5. 在任务结果中查看“功能与需求”和“待处理事项”，结合原文依据进行确认。
6. 按本期范围排除暂不实施的内容；如有拆分不合适，可在结果页统一提交调整说明。待处理事项可查看、修改并批量采纳建议；新业务决定会标记“已确认，待同步 PRD”，不会直接混入正式需求。
7. 确认后生成交付包，将需求清单交给开发 Agent、研发和测试逐项实施与验收。

开发前先完整阅读原始 PRD。清单是查漏和原文导航，不是完整实现规格。完成一项后，回到原文检查相关条件、限制与例外，并在清单记录核对状态及证据。新的业务规则先补入 PRD，再创建新版本分析。

如果更新应用后旧任务提示“检查点版本过旧”或此前因输出校验失败，请在原任务上选择“重新开始”。平台会沿用该任务保存的 PRD、补充资料和本次说明创建一条新任务；原失败记录会保留，旧检查点不会混入新分析。

新版任务会按功能批次保存已经校验通过的结果。执行失败后点击重试，匹配相同输入的成功批次会被保留；平台不会把失败候选当作正式需求，也不会把运行故障当作业务待确认问题。网络故障和模型提交错误会有限重试或修正，仍未完成时保留诊断。

当前结构化分析使用已登录的 Codex CLI。现有 DSH SDK 协议缺少结构化操作能力，选择该适配器会在运行前明确提示不支持，不会静默降级成普通对话。平台不按估算 token 拒绝调用；模型服务自身的容量、额度和上下文限制仍然适用。

## 交付结果

平台基于同一份结果生成：

- `checklist.csv`：七列检查清单，字段为 `feature_id`、`feature_source`、`requirement_id`、`requirement`、`source_location`、`check_status`、`notes`。
- `checklist.xlsx`：同源需求清单、完整待处理事项与阅读说明。
- `pending.json`：问题、已知事实、影响、建议、关联、处理状态和用户决定，包含待同步 PRD 的新规则。
- `sources/files/`：本次任务冻结的原始 PRD 与补充文件；缺少原件时导出明确失败，不用提取文本或图片转录替代。
- JSON 结果快照与按模块的 Markdown 导航：保留范围和关联，供回查使用，不替代原始 PRD。

把完整目录交给编码 Agent，并从包内 `README.md` 开始：先读原件、核对待处理事项，再结合目标代码仓库实现。将 CSV 复制为工作副本，逐项填写 `check_status`（`unchecked` 未核对、`checked` 已结合原文核对、`pending` 待处理）和 `notes`（备注或证据）。清单状态不等于平台已验证业务代码。

“可以交付”表示当前范围已经形成可实施的需求清单，不表示代码已经完成，也不代表 AI 可以证明自然语言意义上的 100% 零遗漏。仍未确认的事项会明确保留在结果中，供后续处理。

业务待确认事项会随需求进入交付包，不阻止已整理需求的导出；开发 Agent 仍须处理相关未决项，不能把建议直接视为已确认规则。平台校验尚未通过的结果只作为草稿保存。

## 本地运行

当前仓库暂未在新 GitHub 仓库发布安装包，可以从源码运行：

```powershell
npm install
npm start
```

Windows 本地打包：

```powershell
npm run dist:win
```

macOS 本地打包：

```bash
npm run dist:mac
```

开发实现、目录职责、关键约束和验证命令见 [AGENTS.md](AGENTS.md)。历史方案与验收证据分别保存在 `docs/spec/` 和 `docs/acceptance/`。
