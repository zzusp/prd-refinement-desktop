# PRD 功能与需求检查清单收敛方案

日期：2026-09-14。状态：分析方案，尚未实施。依据：用户本轮重新明确的平台目标及当前源码；本文件不回写此前方案或验收结论。

## 1. 产品目标

将中大型 PRD 整理为“有哪些功能模块、各模块有哪些要实现的需求”的 checklist，帮助编码 Agent 在处理长文档时保持全局视野，并逐项检查是否漏做。实现依据始终是原始 PRD、相关资料及目标代码，清单是导航和查漏工具，不是替代原文的需求规格书、技术方案、验收规范或 Agent 执行编排器。

粒度属于用户偏好，不制定唯一正确的拆分尺度、每模块条数、每条字数或字段完整度评分。语义忠实属于红线：功能和需求必须存在于 PRD，不增加推测，不把可选改成必须，不颠倒否定，不改变对象、范围或重要限定。

## 2. 当前偏离在哪里

- `src/types.ts:79`：RequirementDetail 同时包含 title、behavior、conditions、constraints、explicitAcceptanceConditions，并维护逐字段 evidenceBindings。这是结构化规格书，而非轻量条目。
- `electron/model-output-schemas.ts:25`、`electron/domain.ts:240`：复杂字段已进入模型契约、证据物化和确定性验收，不能仅在界面隐藏。
- `electron/export-agent-package.ts:174`、`:253`：CSV包含实施、验收及证据字段；交付说明要求以生成包为唯一入口并逐项实施生成的内容，与“实现仍读原PRD”的定位不符。
- `electron/scheduler-v2.ts:110`、`:611` 及 `electron/refinement-adjustments.ts:286`：用户输入可作为 business-fact/replacement，并成为来源单元。这与本轮“PRD中存在”的红线冲突，必须一并收口。
- `electron/scheduler-v2.ts:702`：现有核查已禁止要求增加粒度，只检查产物的原文支持，说明问题并非所有检查都应该删除。原文引用、结构化调用、失败恢复仍有必要；需要删除的是过重的业务表达和推导职责。

三种路线比较：仅隐藏栏目会保留模型成本与复杂校验，排除；直接只留旧title会留下抽象标题、错误证据和旧执行说明，也不能保证语义，排除；推荐整体迁移到“模块分组＋简短需求项＋原文引用”，从类型、流程、调整到导出同步收敛。

## 3. 最小业务模型

模块只承担分组和导航：编号、原文引用、所属需求项。展示名称优先从原文标题或原文片段读取；无明确标题时使用编号和来源位置，不让模型另造目标、边界或模块业务描述。引用复用当前任务冻结输入与 SourceRef，不依赖另一份方案或第二套来源账本。

需求项只保留：编号、所属模块、简短需求表述、原文引用。模块列表和需求项归属关系只持久化一份，其余列表由程序派生。引用复用现有SourceRef及任务冻结输入，不新建第二套规则账本。用于查漏的状态属于导出清单的使用记录，不进入需求语义，也不由分析成功自动勾选。

删除独立的“具体要求/行为正文”“适用角色与触发条件”“限制与例外”“原文明示验收条件”及对应逐字段证据绑定。不是把这些内容拼成一个长段落，也不是把原PRD的每句话机械变成一条需求。

保留语义所必需的限定，但不完整复述实施细节。例如原文“仅允许撤回未审核的申请”，条目可写“撤回未审核的申请”，不能写“撤回任意申请”。页面字段、流程细节和验收说明仍读所链接的原文；原文明示的独立性能、安全、导入迁移等要求如可被独立漏做，也可以作为普通需求项，不因删栏目而整类丢弃。

跨模块要求仍是普通条目：按原文组织在相关模块或公共要求分组中，并保留原文；不由平台推导 depends-on/affects/exception-to 关系图、传播影响或“未满足依赖”执行门禁。不为没有业务含义的文档分组创建伪功能。

## 4. 来源与调整的边界

主PRD决定清单范围。功能和需求的正式引用只指向主PRD；补充资料、历史资料和用户调整描述不能独立创造清单需求。PRD明确引用附件时，清单记录PRD中的引用要求，附件随包供实现时阅读，不另建附件授权推断。不要把任意补件默认提升为需求来源。

用户可要求按模块重组、合并、拆开、缩短表述、按指定原文补漏。允许多种粒度，不以“太粗/太细”自动否决结果；每次生成仍执行同一来源和忠实性红线。

例：“把查询和导出分成两条”可执行；“补上PRD某节的批量导入”查到原文后可执行；“加短信提醒”但PRD不存在时不能写入正式清单，应说明未找到依据，需先更新PRD。不能把这句话转成 USER 来源后绕过检查。

首版沿用现有结果版本/重跑能力：固化原PRD及调整说明后重新整理，保存上一版。可复用文件解析与索引；不复用输入已变的旧模型回执。全局或无法确定影响范围的调整直接完整重跑，不额外建设自动影响分析、多轮任务聚合或复杂增量补丁引擎。调整说明是参数，不是需求证据；无关条目保持原文语义。

## 5. 执行流程

1. **读取原文**：程序保存文件版本、建立索引，登记未读/缺失材料；必要时读图片。该步骤不能用模型摘要替代原文件。
2. **整理清单**：按源文章节或业务段落分批生成模块和简短需求项，再统一重复与分组。全部判断读取原文，不用前一步生成的摘要作为需求依据。用户粒度描述直接作用于此阶段，不再先生成一套完整规格书。
3. **核对原文**：结构校验核对ID、归属、引用存在/范围/文件版本；模型只核对条目及模块是否有据、是否曲解原意。对明确发现的漏项提示来源，可在原文依据下补入；不能以字数、字段数、需求数量或个人偏好强迫再细化，也不再对每句话做全面规则建模。
4. **生成清单**：确定性生成同一份清单的阅读与表格视图，附原文入口。问题修正后重核对被修改内容，有界修正失败保留诊断，不能无限循环或把未验收结果伪装成功。

保留当前类型化Input/Proposal/Result、原生结构化操作、分类故障处理、取消、原子保存、工作单元恢复。简化业务Schema和调用内容，不回退到提示词自由拼JSON，也不恢复token硬预算。节点数量以新职责为准，不强行维持13类旧业务节点。

不再生成业务澄清建议、推荐方案、默认口径、验收设计或关系图。对原文确实存在的冲突/歧义，可在对应来源处显示简短提示，不猜答案；技术资料缺失和模型执行失败独立呈现，不能被降格为业务待办后标记整个分析成功。安全可读的已完成部分可查看，但必须标明分析未完成。

## 6. 用户结果与交付

页面围绕“模块 → 需求清单 → 查看原文”组织；需求行仅显示编号、简短表述和来源入口。原文阅读器保留上下文，不能只显示生成摘要。保留调整输入及重跑结果查看，不再展示四组细节字段、复杂验收/澄清面板和推导关系。

默认交付 `checklist.csv`、简短使用说明及 `sources/` 原PRD/相关资料，文件完整性清单由程序生成。CSV建议7列：模块编号、模块原文标签、需求编号、需求项、原文位置、核对状态、备注/证据。核对状态默认“未核对”，可由使用者记录“已核对/待处理”，它不是平台认证的代码完成状态或业务验收状态。

CSV是对外主要清单；现有Excel导出可保留为相同字段的表格视图，不扩展多套业务表。应用内部继续用结构化快照存储，但不再默认输出冗长requirements.json和各功能规格书供Agent逐字实现。删除旧 implementation.csv 中行为、条件、验收、依赖和双状态等复杂列，文件名改为 checklist.csv，避免定位误导。

交付说明明确：“先读原PRD及相关资料，再实现；用checklist定位和检查遗漏；清单与原文不一致时以原文为准并记录差异；已核对仅表示本次核对结论，不代表平台完成验收。”

来源引用必须可随包打开。精确文字可用现有块内范围；图片或扫描页只有页级位置时如实显示。导出原文件缺失时明确报告缺失，不把 extracted.txt 或模型转录冒充原文。条目和原文版本绑定，重新生成不自动继承旧清单勾选状态。

## 7. 验收与不能承诺的事

硬性验收：类型/Schema/页面/导出均不残留四组细节字段；每个条目有有效PRD依据；用户描述不能充当需求来源；相同快照各视图条目一致；原文链接可打开；坏输入、运行失败、取消和恢复仍受可靠性机制约束。

业务样本必须包含：无依据新增被拦截；否定、必须/可选、角色和适用范围改变被识别；两种不同粒度均可通过；重要限定保留；表格/附录独立要求不因删字段被整类丢掉；用户要求新增PRD外功能不进入结果；原文有歧义时不代填答案。

不追求不同运行的条数完全一致，不把“引用都合法”宣称为语义完全忠实，不把“逐章读过”宣称为100%零遗漏。语义核对仍可能漏判，因此保留原文对照和用户重跑；红线是设计及验收的约束，不是可用Schema数学证明的自然语言保证。

性能验收使用同一冻结PRD、同一模型配置，分别记录调用数、输入/输出token、耗时、粒度和人工发现的问题，不预先承诺固定降幅，也不以减少条目数充当提速成功。
