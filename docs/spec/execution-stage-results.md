# 执行阶段产出摘要设计

## 目标

在不改变现有执行图结构的前提下，为每个阶段增加一行简短的产出摘要，让用户能直接看懂该阶段得到了什么。

## 方案

保留当前七阶段纵向执行图、阶段状态、耗时、模型配置、Runtime 成本和失败恢复操作。仅在阶段名称下增加 `产出：……`，放在现有执行说明之前，作为阶段的第一条辅助信息。

示意：

```text
✓ 功能清单整理                              累计 42 秒
  产出：整理为 10 个功能模块
  已完成全局整理；累计业务调用 1 次
  功能统一模型 · gpt-5.6-sol · 推理 low
```

摘要保持单行、只给结果，不解释过程。空间不足时省略，不把阶段行展开成详情面板。

## 七阶段摘要口径

| 阶段 | 摘要示例 | 数据来源 |
|---|---|---|
| 原文建账 | `产出：读取 3 个文件，建立 186 个原文片段` | 固定输入中的文件和原文单元 |
| 功能候选识别 | `产出：识别出 14 个功能候选` | `featureCandidateBatches` |
| 功能清单整理 | `产出：整理为 10 个功能模块` | `boundaryUnified` 或该阶段冻结结果 |
| 逐功能细化 | `产出：10 个模块，共 77 条需求` | `detailResults` |
| 产物依据核查 | `产出：已核查 10 个功能模块` | `auditedFeatureIds`、`auditWorkStates` |
| 有据修正 | `产出：完成必要修正`；没有修正时为 `产出：无需修正` | `repairs`、`repairedFeatureIds` |
| 结果发布 | `产出：10 个模块、77 条需求已保存` | 最终 `project` 和产物状态 |

## 状态规则

- 等待执行：不显示产出摘要，避免把预计结果写成事实。
- 执行中：只显示已经确认的进度，例如 `产出：已细化 6/10 个模块`。
- 已完成：显示最终摘要。
- 失败：保留已确认摘要，并继续使用现有错误区域展示真实失败原因和恢复操作。
- 旧任务数据不足：不显示摘要，不新增“旧任务未记录”等干扰文案。

## 数据与边界

- 摘要由前端根据现有 `AnalysisTask` 和 `checkpoint` 确定性生成，不增加模型调用，不新增持久化字段。
- 数量必须能从已有数据直接计算；不能确认时使用不带数量的结论或不显示。
- 不展示功能、需求的完整清单，也不新增点击、展开、筛选或跳转行为。
- 不展示 `auditIssues`、`validationFailures` 等内部校验内容。
- 不出现“平台检查记录”“待处理事项”“建议”“主张”或“阻塞分析”。
- 完成摘要只表示阶段执行结束，不表示需求语义 100% 无遗漏。

## 实施范围

1. 增加一个纯函数，根据阶段 ID 和任务检查点生成可选的摘要文本。
2. 在现有 `Progress` 阶段名称下渲染摘要，不调整执行图整体布局。
3. 为七阶段、执行中、失败和旧任务补充摘要测试。
4. 同步 `DESIGN.md` 与 `UX-CONTRACT.md` 的阶段展示说明。

## 验收标准

- 已完成阶段能直接看到一行明确产出。
- 运行中摘要不会把部分结果表述成最终结果。
- 没有可靠数据时不猜测、不补造。
- 页面结构、操作方式、Runtime 信息和成本统计保持不变。
- 不新增模型调用或 Token 成本。
