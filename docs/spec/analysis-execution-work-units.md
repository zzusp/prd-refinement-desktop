# 分析工作单元与可恢复执行

状态：实施前方案，尚未实施。日期：2026-09-14。

本轮修订：按用户要求取消平台 token 预算限制。估算 token 和实际用量仅用于统计，不参与拒绝请求、强制拆批或暂停任务；模型自身上下文限制由 Runtime 返回真实错误。

## 1. 目标与问题证据

目标：让分析规模决定工作单元数量，使工作规划、有效结果判定、恢复和交付使用同一份执行事实。业务功能只承担组织职责，不能同时充当一次模型调用的容量边界。

本次以真实任务 T-14BAB15B 为回归对象。此前只读检查确认：F-001 有 32 条需求、36 个功能来源；审计结合需求和澄清实际读取 41 个来源单元；本地估算完整请求 21,321 tokens，超过平台配置的 audit 16,000 上限。该数字不是供应商返回的上下文超限。

当前实现的因果链：

1. `electron/scheduler-v2.ts` 的 audit 按功能拼入全部需求、相关澄清、原文和全项目需求目录，没有功能内计划。
2. `call` 在获取执行槽位并启动 Runtime 后，才由 `onAttempt` 调用 `assertPromptBudget`；超限检查发生在 prompt 发送前，但容量没有参与工作规划。
3. audit 的 catch 把异常写入 `auditIssueBatches`，并把 `relationBatches` 写成空数组；下一轮以结果数组存在判断是否跳过。
4. `stage` 以回调正常返回标记完成；异常被内部捕获后，失败的功能也计入“已核查”。
5. needs-attention 的 retry 仅重置修正、交付阶段；修正又排除 runtime-output，无法恢复未执行的核查。
6. 页面已有平台分类，但所有平台问题共用业务式“阻塞／影响本期”显示，执行诊断和内容问题的交互仍未分开。

原任务响应含业务资料，原文和完整日志不进入仓库。验收使用本地冻结副本及脱敏结构样本。

## 2. 方案选择及范围

| 路径 | 判断 | 理由 |
| --- | --- | --- |
| 提高上限并增加重试 | 不采用 | 不能消除功能规模无界、失败缓存和恢复错误；相同请求会重复超限 |
| audit 单独拆批并修 retry | 不作为最终方案 | 修正、复核、调整仍可独立拼出超大请求，也仍有多套完成语义 |
| 统一工作单元执行规则，各节点定义业务分解与验收 | 采用 | 容量、依赖、失败、结果复用和完成判定统一，业务检查语义保留在对应节点 |

本次范围：分析调度器中首轮及调整流程的模型调用，包括输入理解、功能识别/统一、细化、依据核查、澄清处理、修正、修正复核和建议生成；以及它们的检查点、用户可见执行状态和交付判定。

资料导入/图像转录继续属于资料准备流程，不借本次改造重写；若这些输入使分析单元无法构造，应在计划阶段准确定位。Runtime 的统一容量及错误契约可以被资料准备复用，但本次不承诺重构材料持久化。

不增加全文需求穷尽补漏，不改变业务范围和细化颗粒度，不引入外部队列服务、数据库或通用工作流 DSL。正式交付资格沿用既定产品口径；本次仅确保其使用有效检查结果。

## 3. 唯一执行路径

冻结输入 → 建立检查责任 → 按节点规则规划工作单元 → 编译及测量完整请求 → 持久化计划 → 执行 → 校验输出 → 提交单元结果 → 推导阶段状态 → 生成及发布结果。

计划可以分阶段展开：细化结果尚未产生时，不提前猜测需求数。上游结果提交后，依据它的内容指纹生成下游计划。父工作仅在全部子工作及必要汇总完成后成功，不能因为分解完成就计为检查完成。

工作图不是自然语言业务关系图。前者描述平台先做什么、依赖哪份结果；后者描述需求间的业务前置、影响和例外。不得互相转换。

## 4. 数据与状态契约

### 检查责任

每个责任保存 kind、目标 ID、输入版本、原文范围和完成条件。检查类别包括需求忠实性、澄清有效性、关系依据、修正效果和回归。生成类工作保存来源处理范围及输出验收契约。

范围必须区分：模型明确选择的支持证据，以及平台确定的核查上下文。后者包含该需求关联的完整来源、结构上下文、适用约束和有效用户决定；不能只用模型自行选择的有利片段进行核查。

覆盖表记录每项责任及其所需原文选区由哪些单元承担，区分“已读取”“结论已联合核查”“未判定”。遍历全部输入不等于语义全部正确。

### WorkUnit

最低字段：

- `id`：kind、责任集合、输入指纹、契约版本和拆分路径的稳定身份。
- `kind`、`subjectIds`、`sourceRefs`、`dependencyIds`、`inputHash`。
- `state`：pending、running、succeeded、failed、cancelled、invalidated。
- `attempts`：尝试编号、执行代次、开始/结束时间、请求指纹、用量测量、错误类别。
- `outputRef`：仅指向已经完成结构、引用和节点范围校验的不可变结果。
- `parentId`、`childIds`：存在分解时记录责任传递；父结果还需执行聚合验收。

模型成功返回与业务检查结论独立。审计输出必须对指定责任逐项返回 `passed | issue | unknown`，以及有依据的问题/关系；缺项、额外项和重复结论均拒绝。调用成功且发现内容错误，可以完成此次核查并进入修正；unknown 表示核查尚未完成，不能当 passed，也不能自动新增业务澄清。

执行故障单独保存为 `ExecutionFailure`，至少区分容量、输出协议、鉴权/配置、临时传输、超时、存储、取消和内部程序错误。业务 `AuditIssue` 只保存核查发现的内容问题。

## 5. 请求编译与运行约束

### 统一请求编译

抽出同一个编译入口，规划和发送使用它生成的实际请求。包含指令、schema、别名映射、原文目录、当前对象、必要关联对象和纠错反馈；禁止规划时测简版输入、发送时再加入全集。原文在一个请求内按固定引用去重，内部长 ID 可使用可逆短别名。

取消平台自行设置的 token 限制：

- 删除节点 token 硬上限、target 拆批阈值及按累计 token 暂停任务的设计，不增加“无限模式”开关或超大常量兜底。
- token 估算与实际输入/输出用量继续保存，用于诊断和成本展示，不影响发送资格、工作拆分或完成状态。
- Runtime 若提供模型容量信息，可记录为诊断信息；不据此另建平台 token 拦截门禁。适配器必须服从供应商真实协议，但不额外施加平台 token 配额。
- 请求按检查责任、文档结构和业务关联分组，分组大小不是 token 配额。完整请求编译后直接进入执行流程。
- 纠错携带定位问题所需的反馈；完整诊断本地保存。界面可折叠诊断，但不能因平台 token 阈值省略必要原文或终止纠错。
- 调用前仍做输入结构、引用、依赖和取消状态检查，并保存请求计量；这些检查不得以估算 token 超限为失败原因。

Runtime 明确返回上下文超限时，记录供应商错误和原工作责任，按本节分解规则生成子工作；不能用本地估算冒充实际超限。输出仍须逐对象回执，截断或缺项不提交部分结果。可拆工作按职责重新分解，保留其联合核查责任。

### 节点分解规则

| 工作类型 | 分解与联合要求 |
| --- | --- |
| 输入理解、功能候选 | 按固定来源位置规划，保留标题/表头/上下文；跨片组织合并保存来源映射 |
| 功能统一 | 分组处理并做跨组边界核对；不能把所有中间结果重新塞进一次无界调用 |
| 逐功能细化 | 按来源和适用约束处理，保存来源覆盖、跨片续接和合并记录；业务功能不强制拆成多个功能 |
| 需求忠实性核查 | 一条需求及必要上下文为基本检查责任；容量允许时多个责任同批 |
| 澄清有效性 | 按问题建立联合证据责任；局部缺证不能判断需要用户回答 |
| 关系核查 | 将关系发现与局部忠实性检查分开；发现候选后再回原文核查真实两端 |
| 修正与复核 | 按受影响责任建立候选；原问题复核与回归责任显式列出；不能只复核模型主动修改的字段 |
| 调整、建议生成 | 按明确目标和有效输入规划，复用同一计量、持久化及输出提交入口 |

Runtime 明确报告单条责任上下文超限时进入证据分片流程：读取固定选区 → 生成带原文引用的事实/定义/条件/例外 → 联合候选 → 逐片核查反证及联合支持。中间事实是派生内容，不升级为新来源。联合候选仍被 Runtime 拒绝时，可按明确子命题继续分解并检查组合结论；无法继续保持语义完整地分解时，该责任保留 unknown/实际容量失败及具体范围。不得宣称任意规模都必然完成。

单个不可合理切分的源片段本身超限，报告输入能力限制，不能静默截断。能按文档结构细分的片段先由来源索引生成稳定子选区，保留父位置和上下文。

## 6. 跨批语义与覆盖

### 需求核查

分批保存每条需求的检查结果，条件、限制和明示验收条款使用稳定字段路径对应到原文。拆批前后都不能删除条款、改变合并颗粒度来缩小请求。核查上下文来自冻结范围，不能由待核查输出自行决定全部范围。

### 澄清联合判断

先检查已有显式关联，再对本轮需求快照中剩余候选分块检查其是否承接答案；仅按同名或共享来源检索不能作为覆盖完成依据。找到候选答案后取回完整相关原文，结合所有相关条件和例外做联合判断。已存在的业务澄清继续保留，但执行 unknown 不赋予它“已核实确实需要业务决定”的新状态。

复用 `clarification-reconciliation.ts` 与 `clarification-relations.ts` 中联合证据、反证和关系三态的业务规则；去掉依赖外层不可见约束的递归重试，把每轮尝试、否决与失效交给工作单元执行器记录。不能仅因历史测试通过就原样搬入。

### 跨需求关系

保留本流程“只处理当前已有需求和原文明示关系”的范围，不扫描未形成需求的全文寻找新需求。

以当前需求快照为候选全集，按业务检查责任分块并显式登记需要检查的块对。块内、块间候选处理不能因检索不命中而被视为已排除；优先级可以由索引决定，责任集合不能据此静默缩减。每个块对处理双方业务主张及可定位的原文关系线索，候选的判断必须取回对应原文；标题目录只用于导航。单对责任被 Runtime 明确报告上下文超限时也走证据联合路径。

同一对需求可能存在两个方向及不同关系类型，处理记录须覆盖协议规定的方向和类型。结果区分发现有据关系、在指定范围未发现、未判定。前两者只代表该次检查完成，不证明自然语言不存在任何关系。

完整块对覆盖最坏为二次规模。本方案接受这一成本并在计划中估算展示，不承诺关系检查线性扩展；可安全排除的集合必须有明确、可审查的产品范围规则。不设置累计 token 停止线；用户取消或实际执行故障时保存进度，不能偷偷减少检查范围。若后续要改成仅核查已有关系、不发现新关系，属于业务能力变更，另行决定。

## 7. 持久化、重试与失效

复用任务目录、串行保存队列和原子 rename。单元结果先写不可变本地文件，再原子保存引用该结果的检查点；引用成功后才允许被下游消费。写结果成功但任务提交失败，仅留下不可见孤立文件，不得显示完成。当前规模不引入数据库。

恢复只信任：状态 succeeded、输出文件存在且指纹一致、所有依赖有效、输入与契约版本一致。字段存在或空数组不能替代这些条件。

应用重启时将未完成 running 尝试记为中断，回到可重排状态；新的执行代次防止迟到响应写入。取消停止排新工作，已返回的迟到结果不得越过代次校验。单个工作失败不取消无依赖的其他工作。

错误恢复策略：

- 平台估算 token 较高：只记录用量，不拒绝、不生成失败、不强制拆批。
- 可识别的供应商上下文拒绝：记录实际失败，按业务责任和原文结构重新分解；不将任何未知错误猜成上下文超限，不反推新的平台 token 配额。
- 临时传输/限流：有界退避；鉴权和配置错误等待配置修复。
- 输出结构错误：一次完整反馈纠错；仍失败则保留失败及诊断。
- 语义 unknown、反证和修正失败：有界定向重审，范围和轮数持久化；达到上限保留未完成责任。
- 程序错误和存储失败：准确记录，不转为业务问题。

模型调用纠错次数、语义修正次数分别持久化，保留有界重试以防同一错误无限循环；不设置任务累计 token 预算，也不要求用户追加 token 配额。普通故障重试只执行失败或未完成单元，不清零已有自动重试计数。超时、并发控制和取消能力继续保留。

输入或产物变更时，依赖按实体内容、来源版本、有效决定、协议、检查策略和适用 Runtime 配置指纹判断。只失效受影响结果及后继；若某次判断依赖整个候选目录，它必须记录目录指纹，新增需求也会使相关负面判断失效。不能因某 ID 未出现在模型输出中就认定其不影响结论。

## 8. 完成、修正与发布

阶段状态由有效工作集合推导。父工作必须收齐有效子结果并通过聚合校验；缺少任何必需责任就是未完成。

审计完成且发现内容问题，会生成显式修正责任。修正先作用于候选快照，复核原问题，并重新建立受影响的忠实性、澄清和关系检查。新快照通过后才提交。发现旁支问题按其责任单独登记，不混进无限修正循环。

检查证明绑定实际范围和依赖指纹。scope coverage、model verdict、business issue、execution failure 独立保存，禁止把“本次没有记录问题”当作通过。

交付读取当前所选范围的有效检查证明与原有业务准入规则。生成文件、回读校验和正式发布另有状态；导出失败只恢复导出，不重跑模型。同一 operationId 只发布一次正式版本，沿用已有任务族提交互斥和基准比较。

## 9. 用户体验

- 执行区域展示“平台核查未完成”、具体阶段、已完成/待处理工作数和继续处理入口。技术诊断折叠；默认说明影响的检查范围与恢复动作。
- 用户需要回答的业务问题、平台发现的内容修正项保留各自语义；执行故障不进入业务澄清计数。
- 任务状态从实际工作推导，不再固定写到 88% 或把失败批次计为已核查。计划动态展开时明确显示“已规划部分”，不制造单调百分比完成假象。
- 草稿可查看；正式交付缺少检查时说明缺少哪项检查，不要求用户用业务回答解决 Runtime 故障。

## 10. 实施结构与复用

| 文件/模块 | 职责 |
| --- | --- |
| `electron/scheduler-v2.ts` | 保留任务队列、并发槽位和阶段业务入口，移除按数组存在跳过和按固定阶段重置的恢复判断 |
| `electron/prompt-budget.ts` 及调用点 | 保留请求计量，删除 token 门禁、硬上限及目标阈值；后续按计量职责命名，不保留空校验函数 |
| `electron/source-evidence.ts`、来源索引 | 固定引用、别名、去重及可追踪分片，继续提供确定性证据校验 |
| `electron/task-execution-state.ts` | 工作状态、依赖有效性、覆盖和阶段状态推导，复用已有内容指纹能力 |
| 新 `electron/analysis-work-planner.ts` | 节点工作规划与父子责任，独立于执行；现有 budget 模块不应承载业务分解 |
| 新 `electron/analysis-work-executor.ts` | 持久化尝试、恢复、错误分类和结果提交，避免继续把状态机堆入 scheduler 大函数 |
| 现有澄清、调整、修正模块 | 保留业务校验和原文联合规则，改为提交工作计划及消费有效结果 |
| `src/types.ts` | 新工作契约、检查责任和独立执行诊断；旧检查点不兼容，不叠加第二套字段判定 |
| 结果页、任务页、导出模块 | 读取同一执行与检查事实，分开显示恢复动作、业务事项和交付状态 |

工作结果文件放现有任务用户数据目录，不提交到 Git。方案和验收留在 docs 对应分类。

## 11. 实施顺序与退出条件

| 阶段 | 内容 | 退出条件 |
| --- | --- | --- |
| 1 | 冻结脱敏错误样本、真实任务输入副本与预期责任；完整请求组成计量 | 重现超预算、错误缓存、重试跳过和错误进度四个反例 |
| 2 | 请求编译、用量计量、工作状态、持久化执行器 | 高 token 请求不被平台拦截，崩溃、取消、失败和迟到响应测试通过 |
