# 任务终态进度修复

## 症状与根因

任务的七个阶段全部结束后，调度器仍用固定 `88%` 表示交付准入未通过；渲染层又把 `needs-attention` 显示为“已完成”。进度、执行终态和交付质量被混成一个字段，造成“已完成 88%”的矛盾。

## 修复口径

1. `progress` 只表示执行路径进度。所有阶段完成并进入终态时为 `100`，不得编码交付质量。
2. `status` 继续区分成功完成、平台未完成和执行失败。`needs-attention` 在用户界面显示为“平台未完成”，不能翻译成“已完成”。
3. `delivery.state` 继续决定正式包或草稿，不因进度到 100 放宽准入。
4. 平台未完成时显示摘要错误和恢复操作，但不重新展示内部 audit issue 列表。
5. 初始化时将阶段均已完成的历史 `needs-attention` 任务规范化为 100%，不改写其交付状态与产物类型。

## 验证

- 调度测试覆盖交付未通过的终态为 `needs-attention/100`。
- UI 测试覆盖“平台未完成”、100% 和恢复入口，并排除“已完成 88%”。
- 用真实历史任务副本验证七阶段完成后显示 100%，内部校验明细仍不可见，草稿/正式包边界不变。
