# PRD 轻量清单与完整分析流程

日期：2026-09-14。状态：调整后的实施前方案，尚未按本方案实现。

本方案替代 `prd-checklist-product-convergence.md`。旧方案中的四阶段重构、删除待处理事项/建议方案、移除既有核查与定点修正职责不再执行。旧文件保留为决策快照。本轮只调整方案及目标记录，不继续修改业务代码。

## 1. 目标与修正范围

平台帮助用户把中大型 PRD 拆为功能模块和需求 checklist，减少编码 Agent 遗漏内容；实现时仍需阅读原始 PRD 和相关资料。同时保留分析时发现问题、澄清未决细节和提供建议方案的价值。

本次精简针对正式需求条目的表达结构。保留原有分析深度、阶段边界、资料处理、待处理事项、建议生成与处理、用户调整、来源核对和错误恢复。不得把精简字段扩大为删除流程，也不能让模型在内部继续生成完整规格书再仅隐藏页面栏目。

核对基线：提交 `3e29713` 的 `electron/scheduler-v2.ts` 中 stages 为七阶段；同文件 detailSchema 同时包含 requirements 和 clarifications，clarificationContract 包含问题分级和 resolutionProposal。`refinement-adjustments.ts` 存在建议采纳与调整处理；`task-execution-state.ts` 保留来源、功能、需求、关系和澄清核查记录。这些是本轮恢复与适配的基线，不将当前未提交的四阶段代码视作已验收实现。

## 2. 保留七阶段和现有职责

| 阶段 | 保留的职责 | 本次适配 |
| --- | --- | --- |
| 原文建账 | 固定输入版本，解析文字/表格/图片，登记位置、材料角色及缺失情况 | 调整说明不得被伪装成原 PRD 事实 |
| 功能内容整理 | 按连贯原文识别功能内容，保留来源分类和相关上下文 | 不凭空补充功能；保留候选核查与定点返工 |
| 功能清单整理 | 合并重复、核对归属和边界，保留原文明示的跨功能约束 | 模块承担分组导航，不扩写业务目标 |
| 逐功能细化 | 阅读功能对应的完整原文和适用上下文，识别需求及未决细节 | 输出简短需求项，同时保留完整待处理事项和建议 |
| 产物依据核查 | 核查来源、语义、已有答案、重复问题及原文明示关系 | 根据条目、待处理事项、建议的不同性质分别核对 |
| 有据修正 | 对问题定点修正、复核，保留写入范围与失败诊断 | 适配简化后的需求字段，不删除修正和复核机制 |
| 结果生成 | 生成清单、待处理事项和原文入口，记录实际状态 | 改为查漏用途说明，不宣称产物可替代 PRD |

原有功能整理中的分类/覆盖核查、当前功能范围内的澄清与已有答案核查、关系核查、局部修正、执行回执和断点恢复继续保留。不额外引入全面重扫或“每句话都必须单独成项”的门禁。关系仅承接原文明示关系，不推导技术实现顺序。基线仓库虽保留独立澄清重整模块，但调度并未调用；本轮不把这段不可达代码新接入流程。

保留现有类型化 Input/Proposal/Result 与结构化调用通道。节点只因需求字段变化做必要适配，不再统一缩成 image/checklist/audit 三种契约。不恢复 token 硬预算。

## 3. 两类分析结果

### 正式需求清单

只表达编号、所属模块、简短需求表述和原文引用。原文显示名称、来源编号、状态、关联关系等组织与追溯信息复用现有机制；不为本轮强行重建整套领域对象。

删除需求项中的独立“具体要求”“适用角色与触发条件”“限制与例外”“原文明示验收条件”字段，以及对应逐字段证据生成。需求文本绑定条目级证据，不把被删字段拼成一个长段落。

条目必须来自 PRD，并保留必要语义。例如“仅允许撤回未审核的申请”可整理为“撤回未审核申请”，不能变成“撤回申请”后让人误解适用范围。枚举、控件细节、字段说明等通过原文入口阅读；原文明示且可独立漏做的能力可以列为单独需求，但不强制把每个字段细节拆为一项。

### 待处理事项与建议方案

继续保留问题、原文明示事实、待决定点、影响、级别、关联功能/需求、来源和处理状态。建议继续包含具体方案、理由、影响或取舍、需要用户确认的内容，必要时提供有意义的备选。

分析可以发现 PRD 未说明的细节。问题应指向 PRD 已存在的功能或业务情境，说明原文已知什么、缺少哪个决定、为何影响理解或实施；不要求“问题本身必须逐字出现在 PRD”。对“原文没有说明”的判断，需要核对相关上下文，不能因局部分片没看到就断言整份 PRD 缺失。

建议允许提出原文之外的解决思路，明确作为待决定的建议。它的依据用于说明问题背景与推荐理由，不伪装成“PRD 已规定该方案”。不把任意新功能、一般最佳实践或技术选型清单灌入待处理事项；与当前 PRD 没有具体关系的扩展不自动生成。

示例：PRD 明确批量合并，但未说明部分数据不满足条件时如何处理。

- 清单：按 PRD 整理“批量合并符合条件的数据”。
- 待处理事项：部分数据不符合条件时，是整批拒绝还是只处理符合条件的数据？关联该合并功能及相关原文。
- 建议：提出可选处理方式及影响，标明尚待确认。建议本身不成为正式需求。

保留现有问题分级；“阻塞”描述相关业务决定对实施的影响，不意味着整个分析无法产出清单。仅有表达性问题且无需用户决定的，沿用现有轻微事项处理；不得为填满级别模板虚构默认业务规则。

## 4. 区分有据整理与建议决策

| 内容 | 判断标准 | 可以进入正式需求吗 |
| --- | --- | --- |
| PRD 明确要求 | 引用有效，表述不增删关键语义 | 可以 |
| PRD 已有答案但清单遗漏 | 回查原文，补充或修正；不再向用户重复提问 | 可以 |
| PRD 存在冲突、缺失决定或影响实施的未决细节 | 关联真实情境，核对上下文，说明问题与影响 | 作为待处理事项保留 |
| 模型提出的建议方案 | 明确推荐理由、取舍和待确认性质，不假称原文结论 | 不直接进入 |
| 用户采纳/修改建议 | 保存用户明确决定和处理历史，与模型建议区分 | 无 PRD 依据时不自动进入 |

用户采纳建议的入口保留。若该处理只是纠正对既有 PRD 的理解，可引用 PRD 更新清单并关闭已回答问题；若采纳新增或改变了业务规则，保存为已确认的补充决定，提示同步 PRD，不能仅把状态改为“已采纳”便转换为原文需求。PRD 更新后以新输入快照重跑并建立新版本的来源关联。可展示“已确认，待同步 PRD”的处理结果，不自动编辑原文件。

原文事实、未决问题、建议、用户决定各有明确身份。对建议不套用“内容必须在原文逐字存在”的正式需求规则；对正式需求也不放宽为“模型觉得合理或用户点过采纳”。

## 5. 用户调整和重跑

保留当前调整、建议采纳、结果版本和局部重算机制。本次不把所有调整统一改为全量重跑，不删除现有调整解析/校验/复核通道。

- 粒度与组织意见：按用户描述拆分、合并、重组和缩短条目，仍读取原 PRD 并保持语义。无唯一正确粒度，不以条数、字数或栏目齐全为验收标准。
- 指定原文补漏：定位 PRD 后补入已有要求，重新核对受影响结果。
- 问题和建议处理：保留用户采纳、编辑、暂缓及既有状态能力，按上一节区分原文结论与新增决定。
- 新增业务意图：不再转成 USER 来源绕过 PRD 红线；有相关业务情境时作为待处理决定记录，进入正式需求前需更新 PRD。

调整作用范围沿用已有定位与校验机制；全局调整或 PRD 输入版本变化才按相应范围重新分析。未受影响结果不因本轮精简而被无条件重做；输入改变的回执不能当作新输入的验收证据。

## 6. 页面与交付

结果页保留“功能/需求清单”和“待处理事项”。需求行精简为短文本、来源入口及必要关联；待处理事项仍可查看背景、影响、建议与处理记录。调整输入继续保留。现有任务、进度、执行记录和 Runtime 配置不因本轮精简而收缩。

交付保留两类内容及关联：

- `checklist.csv`：模块编号、模块标签、需求编号、需求项、原文位置、核对状态、备注；具体实现时继续读取原 PRD。待处理事项通过关联的需求/模块编号定位，不把建议正文塞入需求项。
- Excel：同源需求清单与独立待处理事项工作表，后者包含建议和处理状态。
- `pending.json`：复用现有待处理事项机器文件，携带问题、来源、关联对象、建议及用户处理记录；已确认但未同步 PRD 的决定仍应可见。
- `sources/` 与说明、清单文件完整性信息：随包保留原 PRD 和相关资料。

结构化快照及其他既有导出按简化后的字段适配，不因为本次定位调整强制删除；去除“生成包为唯一实施依据”的说明。已有待处理事项不阻止包生成，也不能从包中消失。平台执行失败须如实标记未完成，不能包装成业务待处理事项后宣称执行通过。

## 7. 实施顺序

1. 对比基线与本轮改动，恢复误删的七阶段调度、现有逐功能澄清/关系核查、定点修正、建议 IPC、调整处理、待处理界面及对应测试。仅回退本轮修改，不把基线未接入的独立澄清重整模块新增为生产阶段，也不触碰其他未提交工作。
2. 在原流程上缩减正式需求 Schema、证据物化与文本表达；同步细化、核查、修正、调整的请求/结果契约。不要保留完整规格书生成作为隐藏成本。
3. 保留待处理事项和建议的内容与处理能力，修正建议采纳自动成为 PRD 事实的边界；更新关联、状态、指纹和复核条件。
4. 同步轻量需求展示、完整问题处理、CSV/Excel/pending 导出与说明。
5. 验证原流程功能回归、正式需求红线与问题发现能力，再跑真实任务；不将已撤回四阶段分支的测试计为新方案验收。

## 8. 验收和未收敛边界

必须验证：七阶段及原工作单元恢复仍在；需求不再生成四组过度字段；不同粒度可接受；关键限定不丢；明确需求只能来自 PRD；能够发现关联现有功能的缺失决定并提供建议；已有原文答案不会重复成为待处理事项；建议不能自动变为需求；用户处理可保存且与 PRD 来源区分；导出保留问题、建议、关联及原件；有未决业务问题仍可生成清单；执行异常保持真实失败状态。

“有价值的问题发现”没有单靠 Schema 可证明的标准，需用真实 PRD 抽样审阅相关性、遗漏与过度提问，同时设置反例：原文已有答案、无关常识建议、虚构新功能和丢失限定。恢复七阶段本身不能证明语义正确或零遗漏，也不以固定问题数衡量分析深度。

当前四阶段试验 `T-4CC151DF` 的本地摘要显示 status=failed、audit 阶段失败，包含范围限定丢失等模型核查报告；这些尚未逐项人工裁决，不据此断言删阶段是失败的唯一原因。该试验不满足本方案验收，失败证据保留在当前特性验收目录的记录中。
